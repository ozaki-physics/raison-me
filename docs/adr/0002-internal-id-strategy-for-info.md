# ADR 0002: info 系内部 ID を UUID v7 に統一する
ステータス: Accepted

## 背景(コンテキスト)
`info/authN` では、`account_id` や `pass_id` のような内部 ID を `xid` とプレフィックスを組み合わせた文字列で表現しようとしていた。
具体的には `a-...` や `p-...` のように、ID 自体へ種別を埋め込む方針である。

一方で、これらの ID は DB に保存された後は不変であり、ユーザーへ表示する前提もない。
そのため、内部 ID に種別や業務上の意味を持たせるべきか、識別子としての責務に限定すべきかを整理する必要が生じた。

## 課題
`info` 系で使う内部 ID について、以下を明確にする必要がある。

- `account_id` や `pass_id` のような内部 ID に、`a-` や `p-` のような意味を持たせるか
- 一意性のための識別子として標準 UUID を採用するか
- 種別や役割の区別を ID に埋め込むか、別の属性で表現するか

## 決定
以下を採用する。

- `info` 系でユーザーに表示しない内部 ID は UUID v7 を使う
- `a-` `p-` `u-` のようなプレフィックス付き独自フォーマットは採用しない
- 内部 ID の責務は一意な識別に限定し、種別や役割は別カラム、別テーブル、または型の責務で表現する
- `AccountID` と `PassID` のような識別子の区別は文字列フォーマットではなく型で表現し、開発時に取り違えた場合はコンパイル時に検出できるようにする
- `user_id` のような業務上の意味を持つ ID は本 ADR の対象外とする

## 検討した選択肢
1. `xid` とプレフィックスを組み合わせた独自 ID を継続する
2. 独自フォーマットの文字列 ID を自前で設計する
3. UUID v7 を内部 ID として採用する

## 決定理由
内部専用で不変の ID に種別を埋め込んでも、識別子としての本質的な価値は増えない。
むしろ、生成、検証、復元、テストデータ作成のたびに独自ルールを維持する必要があり、実装責務が増える。

種別や役割は、識別子の文字列に載せるよりも別の属性として保持した方が責務分離として自然である。
これにより、ID は一意性に専念し、業務上の意味はスキーマやドメインモデル側で管理できる。

一方で、アプリケーションコード上では識別子の種類を区別できた方が安全である。
`PassID` を要求する箇所へ `AccountID` を渡した場合のような取り違えは、実行時ではなくコンパイル時に検出したい。
そのため、意味は文字列フォーマットへ埋め込まず、型システム側で表現する方針とする。

また、UUID v7 は標準形式であり、将来の DB 設計、API 連携、ログ解析、他サービスとのデータ受け渡しでも扱いやすい。
時系列に基づく並びの局所性もあるため、完全にランダムな UUID v4 より内部 ID として採用しやすい。

## メリット: 期待される効果
- ID 生成とバリデーションの実装を単純化できる
- プレフィックス依存の独自ルールを減らせる
- 内部 ID の責務を一意性に限定できる
- 識別子の種類を型で分離することで、開発時の取り違えをコンパイル時に検出しやすくなる
- 標準 UUID を使うことで将来の連携や移行で扱いやすくなる

## デメリット: 受け入れるリスク
- 文字列を見ただけでは種別を即座に判別しにくくなる
- UUID v7 の生成責務を DB 側かアプリ側かで別途決める必要がある
- 既存のプレフィックス前提コードやサンプルデータは将来更新が必要になる

## 影響範囲
- コード: `backend/info/authN/domain/id_value.go` とそれを利用する ID 値オブジェクト群は、将来 UUID v7 前提の実装へ見直す対象になる
- テスト: プレフィックス前提のテストを UUID v7 の生成、復元、バリデーション前提へ更新する必要がある
- 運用: DB カラム型、生成方法、既存データ移行の方針は別途設計が必要になる

## 将来の考慮事項
- UUID v7 を DB の `uuid` 型で保持するか、文字列として保持するか
- UUID v7 の生成を DB 側に寄せるか、アプリ側に寄せるか
- 型ごとの UUID ラッパーをどう設計するか
- 既存のサンプル JSON やテストデータをどう更新するか
- `user_id` のような業務 ID と内部 ID の責務をどう整理するか
