# ADR 0001: パスワードハッシュにおけるソルト/ペッパーの扱い
ステータス: Accepted

## 背景(コンテキスト)
パスワード認証では、ログイン時の検証に必要な値と秘密として守るべき値が混同されやすい。
特にソルトは「保存してよいのか」「毎回変わると照合できないのではないか」という誤解が起きやすい。
一方で、運用上の追加秘密をどこに置くべきかも整理しておかないと、DB や永続化ファイルに秘密値を混在させやすい。

現行実装では bcrypt を使ってパスワードをハッシュ化している。
この前提に整合しつつ、将来ハッシュアルゴリズムが変わっても通用する設計原則として、ソルトとペッパーの扱いを記録する。

## 課題
パスワードハッシュに関する以下を明確にする必要がある。

- ソルトの役割と秘密性
- ログイン時に何を使って照合するか
- ペッパーを使う場合の保存場所
- プレゼン層、ハッシュ化処理、設定管理の責務分担

## 決定
以下を採用する。

- ソルトは各 credential ごとに異なるハッシュ条件を与える公開パラメータとして扱う
- ソルトは秘密情報としては扱わず、保存済みハッシュに含めるか、同等に再取得できる形で保持する
- ログイン時の照合は、保存済みハッシュに含まれる条件を使って入力パスワードを検証する
- クライアント送信値と保存済み値の単純な文字列一致比較は行わない
- ペッパーは追加秘密として扱い、DB や永続化ファイルには保存しない
- ペッパーを使う場合は Secret Manager または環境変数からアプリ起動時に注入する
- プレゼン層は平文パスワードを受け取り、ハッシュ化と照合は hasher に閉じ込め、秘密値の供給は infra/config が担う

## 検討した選択肢
1. ソルトを秘密値として DB 外で管理する
2. ソルトを保存済みハッシュに含め、ペッパーだけを秘密管理する
3. ソルトもペッパーも明示的に扱わず、実装ごとに判断する

## 決定理由
ソルトは、同じ入力でも credential ごとに異なる結果を得るための検証条件であり、秘密である必要はない。
むしろ保存済みハッシュに紐づく形で保持できないと、登録時と同じ条件でログイン検証を再現できない。

一方、DB 漏えい単独では取得できない追加秘密が必要なら、それはソルトではなくペッパーとして分離する方が責務が明確である。
この分離により、検証可能性と秘密管理を別々に設計できる。

また、bcrypt のように保存済みハッシュ側にソルト等の検証条件を内包できる方式は、ログイン時に新しいハッシュ文字列を生成して比較しない。
保存済み表現を基準に入力値を検証するというモデルと整合する。

## メリット: 期待される効果
- ソルトを保存してよい理由を設計原則として説明できる
- ログイン時に毎回同じハッシュ文字列を再生成する必要がないことを明文化できる
- ソルトとペッパーの責務と保存場所を混同しにくくなる
- bcrypt 以外のハッシュ方式へ移行しても残る設計原則になる

## デメリット: 受け入れるリスク
- 抽象化した記述のため、具体実装の細部までは示さない
- ペッパーのローテーションや失効戦略は別途設計が必要になる
- 既存コードに固定 salt 的な概念があるため、用途の違いを読み分ける必要がある

## 影響範囲
- コード: 直接の実装変更はない。現行の bcrypt 実装は `backend/info/authN/domain/password_value.go` を参照する。固定 salt 的な実装は `backend/info/authN/domain/crypto.go` を参照する
- テスト: なし
- 運用: ペッパーを導入する場合は Secret Manager または環境変数の管理対象が増える
